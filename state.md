## Decisions
- [2026-08-22] Owner rejected the Stripe-hosted Checkout redirect in favor of an embedded, custom-branded `/checkout` page. Implemented via Stripe's Payment Element (`@stripe/stripe-js` + a themed `appearance` config) rather than building fully custom raw card-number/expiry/CVC inputs — a fully custom card form would pull this app into a much stricter PCI-DSS compliance scope for essentially no visual benefit over a themeable Stripe-hosted input, since Stripe's Element can already be restyled to match the site's colors/fonts/border-radius. Switched the underlying Stripe object from a Checkout Session to a PaymentIntent as part of this, since Sessions are Stripe's hosted-redirect primitive — PaymentIntents are the one meant for embedding directly into your own page.
- [2026-08-22] Paywall design, all confirmed with the owner via `AskUserQuestion` before building: (a) one-time $9.99 full-access purchase over a subscription or per-story purchases — no recurring billing/renewal complexity; (b) Supabase Auth (email magic link, passwordless) added specifically to identify paying users, since the app previously had zero user accounts; (c) a fixed free tier of the 5 oldest stories, over a metered "first N you open" paywall — deterministic and stable as new (paywalled) stories keep publishing, rather than shifting which stories are free over time.
- [2026-08-22] Enforced the paywall server-side (the story-detail API withholds the body entirely for locked stories) rather than only hiding it in the UI — a determined reader inspecting network requests still can't get the text without paying. Traded off full SSR-correctness for simplicity: the initial server-rendered response never has the browser's Supabase session (which lives in `localStorage`, not a cookie), so it always renders "locked" first; a client-side re-fetch with the session's bearer token unlocks it a moment later for an already-paying reader. Considered switching to a cookie-based Supabase session (`@supabase/ssr`) to make this correct on first paint, but judged the added complexity not worth it for a kids'-story paywall — the brief flash of "locked" for a paying reader is an acceptable UX cost.
- [2026-08-22] Used a server-created Stripe Checkout Session (redirect flow) instead of Stripe.js/Elements — means no Stripe publishable key is needed at all client-side, and no card-handling code in the app (Stripe's hosted page does that).
